## PR #24 — opencode v2 migration (`668be51`)

### F24-1 — High — Stream deltas and projected snapshots use different part IDs, so a mid-stream history refetch duplicates or segments assistant text `re-verified` `fixed 2026-10-01`

- **Fixed:** `chat.ts` now projects text/reasoning parts with the streaming scheme
  (`${messageID}:text:${ordinal}` / `${messageID}:reasoning:${ordinal}`, ordinal
  numbered per kind — the same semantics as opencode's own v2 reducer), and
  `mergeLiveMessages` keeps the live text/reasoning parts when a mid-step
  projection is applied (the projection omits the accumulated text until the
  step closes, see open question #1). Tests: projected-snapshot-then-delta
  reducer case, per-kind projection IDs, merge cases and a `useMessages`
  refetch case.

- **Evidence:** `packages/client-core/src/chat.ts:195` (`appendDelta` builds
  `id = ${messageID}:${kind}:${ordinal}`; `setStreamText` uses the same scheme)
  vs. `packages/client-core/src/chat.ts:110` (user text part is
  `${message.id}:text`) and `:132` (`toChatMessage` projects assistant content
  with `id = ${message.id}:${index}`). Tool parts merge because they are matched
  by `callID`, not by `id` (`chat.ts:295`).
- **Why it matters:** `useMessages` refetches the full history every 3 s while
  the session is busy (`packages/client-core/src/hooks.ts:95`) and
  `session.execution.started` invalidates the history query
  (`hooks.ts:206`). When the refetch resolves, the cache is replaced by the
  projection; the next `session.text.delta` / `.ended` no longer finds its part
  and appends a **second** text part (the web renders it as separate paragraphs,
  `MessageContent.tsx:237`). If the projection omits the in-flight message, the
  accumulated text is lost until `*.ended`.
- **Fix:** unify the ID scheme — project `content[index]` to
  `${messageID}:${kind}:${ordinal}` (or map the event `ordinal` to the projected
  index) — or preserve/live-merge the streaming parts when a snapshot is
  applied.
- **Tests:** a reducer test that does `setQueryData` with a projected message
  and then emits a delta for the same part, asserting a single part with the
  accumulated text. Close open question #1 below to decide whether the in-flight
  text is present in the projection.

### F24-2 — Medium — Full-history refetch with a silent 10k cap that drops the newest messages `fixed 2026-10-01`

- **Fixed:** `listAllMessages` now walks the v2 cursor pages with `order=desc`
  and reverses the accumulated pages, so the 50-page cap drops old history and
  never the newest messages. The BFF's `sessionsInDirectory` is cached per
  directory for 5 s (`sessionsCacheMs`, cleared on session/workspace mutations
  **and** on the hub's `session.created`/`session.deleted` events, so subagent
  children created out of band appear immediately), absorbing concurrent polls.
  Tests: descending page walk with URL assertions, cache hit, mutation and
  event invalidation, and TTL expiry. The client still refetches the full tail
  every 3 s while busy; a true tail fetch with on-demand paging is left as a
  possible follow-up if sessions ever reach the cap.

- **Evidence:** `packages/client-core/src/client.ts:180-199` walks
  `order=asc` + `cursor.next` up to `MAX_MESSAGE_PAGES` (line 102) × 200
  messages; with the 3 s busy refetch (`hooks.ts:95`) a long session re-downloads
  everything on every tick, and once the cap is hit the newest messages are the
  ones dropped (truncation happens at the start). The same pattern exists in the
  BFF: `sessionsInDirectory` (`apps/server/src/app.ts:120-142`) walks up to 50
  pages per directory on every `GET /api/workspaces/:id/sessions`, which clients
  poll every 10 s.
- **Fix:** while a stream is active, rely on events plus an initial tail fetch
  (`order=desc`, first page, then reverse) and page backwards on demand; in the
  BFF, cache or bound the per-directory aggregation.

### F24-3 — Medium — The E2E mock never delivers `server.connected`, so reconnect recovery has no E2E coverage `re-verified` `fixed 2026-10-01`

- **Fixed:** `openStream` registers the response before emitting the frame, and
  the mock gained `/e2e/offline|online|state` control routes (503 + close its
  SSE clients while offline, plus catalog request counters). The new
  `e2e/tests/reconnect.spec.ts` loads the composer with opencode offline (waiting
  for the client's `retry: 1` to fail too), brings the mock back and asserts the
  catalogs repopulate and a new `/api/agent` request is made — only the hub's
  reconnection (and the forwarded `server.connected`) can trigger it. Verified
  red without the ordering fix and green with it.

- **Evidence:** `e2e/mock-opencode.ts:137-138` — `broadcast("server.connected",
  {})` runs **before** `sseClients.add(res)`, and `broadcast` only iterates
  already-registered clients (`mock-opencode.ts:119-129`). The connecting client
  never receives the event, although the v2 contract says it is the first frame
  (`docs/opencode/events.md:15`) and it is exactly the recovery signal PR #25
  relies on.
- **Fix:** register the response first, then emit (or write the frame directly
  to `res`). Add an E2E that exercises the recovery path (e.g. reload the page
  with the mock's event stream dropping, or restart the mock's event
  connections) and asserts the agent/model selectors repopulate.

### F24-4 — Medium — Stale pending permissions are never removed on reconnect `re-verified` `fixed 2026-10-01`

- **Fixed:** `syncPermissions` (web and mobile) now reconciles instead of only
  adding: each queried directory reports whether it answered, and sessions in
  the answered directories are covered by the server snapshot (via
  `reconcilePermissions` in `client-core`), so a permission answered elsewhere
  is pruned while other workspaces' requests are kept. A directory that fails
  stays uncovered, so a transient error never hides a live dialog. New
  `e2e/tests/permissions.spec.ts` answers a pending request out-of-band (the
  mock resolves it without broadcasting `permission.replied`), reconnects and
  asserts the dialog disappears; verified red without the prune.

- **Evidence:** `apps/web/src/App.tsx:162` and `apps/mobile/App.tsx:252` —
  `syncPermissions` returns early when `pending.length === 0`, so it only adds
  and never prunes. If a permission was answered on another device while this
  client was offline, the dialog stays visible; answering it targets a
  non-existent request and shows "Could not answer the permission request".
- **Fix:** replace the local pending list with the server's actual pendings (or
  remove IDs that are no longer returned), keeping `permission.replied` for the
  live online case.

### F24-5 — Low — SSE parser corrupts CRLF frames split across chunks `fixed 2026-10-01`

- **Fixed:** both copies hold a trailing CR until the next chunk arrives, so a
  CRLF pair split across chunks collapses into one line ending, while a lone CR
  stays a terminator and CR+CRLF still produces the blank line that ends a
  frame. Boundary tests added in `apps/server/test/sse.test.ts` and
  `packages/client-core/test/sse.test.ts` (the pair case fails against the old
  per-chunk normalization in both). Each file now points at its duplicate:
  F24-13 stays open because the Node BFF build and the browser clients share no
  module (and a shared package would need its own build pipeline).

- **Evidence:** `apps/server/src/sse.ts:38` and `packages/client-core/src/sse.ts:38`
  normalize CRLF **per chunk**; a chunk ending in `\r` plus a chunk starting
  with `\n` became an empty line (spurious frame separator). The CRLF test
  (`apps/server/test/sse.test.ts:36-39`) used a single chunk, so it did not
  cover the boundary. Real impact today is nil because the stack emits LF, but
  both parsers accept CRLF from upstream.

### F24-6 — Low — `/api/session/active` poll can clobber the event-set `busy` state `fixed 2026-10-01`

- **Fixed:** `useSessionStatuses` merges the snapshot into the cache through
  `mergeStatuses` instead of replacing it: a status set by an event at/after the
  poll's `requestedAt` wins over the snapshot (they raced), any other status
  missing from the snapshot is idle and gets dropped, and the snapshot wins for
  the sessions it reports. `setStatus` stamps each event write per query client
  (module `WeakMap`). Tests: the pure merge cases, a hook test where
  `execution.started` lands while the snapshot request is still pending (busy
  survives) and a cached status with no fresh event (cleared by the snapshot).

- **Evidence:** `packages/client-core/src/hooks.ts:75-82` +
  `packages/client-core/src/client.ts:286-291`: `statuses()` replaced the whole
  cache with the server snapshot. A poll issued just before
  `session.execution.started` could resolve after it and erase `busy`, hiding
  the Stop button until the next poll.

### F24-7 — Low — `toolState` can throw on an `error` state without payload `re-verified` `fixed 2026-10-01`

- **Evidence:** `packages/client-core/src/chat.ts:55-61` — the fallback branch

### Open questions (PR #24)

1. **Answered (2026-10-01, live opencode 2.0.21):** the projection includes
   the in-flight assistant message, but its accumulated text appears **only
   when the step closes** (`time.completed` set). Measured with a live prompt:
   `session.text.delta` events arrived over ~4 s while every 120 ms poll of
   `GET /api/session/:id/message` returned `content` with empty text; the full
   text (2 567 chars) was present only once `time.completed` was set. So a
   mid-step refetch manifests as temporary loss unless the live parts are
   merged — `mergeLiveMessages` (F24-1) does that, and the reducer test pins it.
2. **Fixed (2026-10-01):** each subscriber write now attaches a rejection
   handler — `stream.writeSSE(...).catch(() => { closed = true; unsubscribe() })`
   — so a client disconnecting mid-write marks the subscription closed instead
   of risking an `unhandledRejection` (the handler is a no-op when the write
   resolves).
3. **Answered (2026-10-01, live opencode 2.0.21):** cursor pages keep the
   `order` of the first page. Probed with `order=asc&limit=1` (page 2 was the
   next-older message) and `order=desc&limit=1` (page 2 was the next-newer
   message), with `order` only on page 1. `listAllMessages` (F24-2) relies on
   this for the descending walk; the E2E mock now honors
   `order`/`limit`/`cursor` the same way.

## PR #25 — catalog recovery fix (`4eac5f7`)

Verdict at review time: sound and shippable. `server.connected` is the correct
signal (first upstream frame, forwarded unfiltered by the hub), the event names
match `@opencode/schema@2.0.21`, and `invalidateOnReconnect` covers
sessions/messages/statuses/directories/catalogs. The items below are optional.

### F25-1 — Low — Catalog "coalescing" is a throttle, not a debounce; the "single refetch" claim can be false `fixed 2026-10-01`

- **Fixed:** `refreshCatalogs` now clears and reschedules its timer (trailing
  debounce), so a burst that spans the 250 ms window still produces a single
  refetch. Test: events 200 ms apart do not refetch at t=250 and refetch once
  at t=450 (a throttle would have fired twice).

- **Evidence:** `packages/client-core/src/hooks.ts:139-149` — the guard
  `if (catalogRefreshTimer !== null) return` did not reset the timer, so a burst
  spanning more than 250 ms (events at t=0 and t=260) triggered two refetches.

### F25-2 — Low — Double invalidation when BFF and opencode restart together `[-]` intentionally left open

- **Note (2026-10-01):** coalescing would debounce every reconnect recovery to
  save ~6 requests in a full dev-stack restart; the current behavior is correct
  and self-healing, so it is not worth the extra timing state.

- **Evidence:** `apps/web/src/App.tsx:173-176` (`onConnect` →
  `invalidateOnReconnect`) and `hooks.ts:168-174` (`server.connected` →
  `invalidateOnReconnect`) fire in the same window during a full dev restart.
  `invalidateOnReconnect` has no debounce and `invalidateQueries` refetches with
  `cancelRefetch: true`, so the second round cancels and relaunches in-flight
  requests (~6 extra requests). Nothing breaks; optional coalescing only.

### F25-3 — Low — `server.connected` does not reconcile pending permissions `fixed 2026-10-01`

- **Fixed:** `EventHandlerCallbacks` gained `onServerConnected`, invoked from the
  `server.connected` case; web and mobile wire it to `syncPermissions`, so a
  permission asked during a BFF↔opencode partition is recovered even when the
  `directories` query keeps the same reference. Unit test added.

- **Evidence:** downstream `onConnect` also calls `syncPermissions()`
  (`apps/web/src/App.tsx:175`, `apps/mobile/App.tsx:265`), but the
  `server.connected` path (`hooks.ts:168-174`) does not. The target scenario
  recovers indirectly (the `directories` query changes identity and the effect
  re-runs), but with `directories` already cached the structural sharing keeps
  the same reference and a permission asked during a BFF↔opencode partition may
  stay hidden until reload. Pre-existing limitation; this PR improves it.
- **Fix:** add an `onReconnect`/`onServerConnected` callback to
  `EventHandlerCallbacks` and run the same recovery as `onConnect` from it, or
  document the limitation.

### F25-4 — Nit — The coalescing test does not pin each of the four event types `fixed 2026-10-01`

- **Fixed:** an `it.each` over `agent.updated`, `model.updated`,
  `provider.updated` and `models-dev.refreshed` asserts one refetch of both
  catalogs per event, so removing any `case` turns a test red.

- **Evidence:** `packages/client-core/test/hooks.test.ts:85-101` emitted all four
  types and only asserted one refetch / two invalidations. Removing a `case`
  (e.g. `provider.updated`) kept the test and typecheck green.

### F25-5 — Nit — The recovery test omits `directories` and the total count `fixed 2026-10-01`

- **Fixed:** the `server.connected` recovery test now asserts all six
  invalidations (`toHaveBeenCalledTimes(6)`, including `directories`) and the
  `onServerConnected` callback.

- **Evidence:** `packages/client-core/test/hooks.test.ts:74-83`. The gap is
  covered elsewhere (`hooks.test.ts:525-535`) but a `toHaveBeenCalledTimes(6)`
  plus the `directories` assertion would make it self-contained and detect
  invalidations added or removed later.

### F25-6 — Nit — The catalog refresh timer has no dispose `[-]` intentionally left open

- **Note (2026-10-01):** the handler is an app-level singleton (`useMemo` for the
  app lifetime), so there is no leak to dispose. Adding `dispose()` plumbing
  would be dead API (see F24-11); revisit only if per-component handlers appear.

- **Evidence:** `hooks.ts:141`. The handler is an app-level singleton through
  `useMemo` (`App.tsx:100-115`, mobile `226-241`), so there is no practical leak.
  Only matters if a per-component handler is ever created.
